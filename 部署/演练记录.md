# 部署演练记录（2026-10-31）

> **重要说明：本次演练是在本机 Docker 容器里搭的「假服务器」上做的，不是正式环境。**
>
> - 假的部分：服务器（本机 Docker 里的全新 Ubuntu 24.04 容器）、域名指向（容器内 hosts 把 `www.evoldream.tech` 指向 127.0.0.1）、HTTPS 证书（自签名证书，模拟 certbot 签发的文件位置）。
> - 真的部分：交付的代码包、数据包、`SHA256SUMS`、`nginx.conf`、两个 service 文件、部署手册里的**每一条命令**、预检/验证脚本——全部是即将交给前辈的原版交付物，一个字没改。
> - 演练方式：模拟一位「只拿到交付包和手册」的部署者，从 `sha256sum -c` 开始严格按手册 S00→S11 执行，不看任何额外资料。

## 四、本次演练**没有**覆盖、只能在正式环境验证的事

| 项 | 原因 | 正式部署时怎么确认 |
|---|---|---|
| DNS 解析到真实服务器 | 假环境用 hosts 模拟 | 手册 S06 前 `dig +short www.evoldream.tech` |
| certbot 真实签发证书 | 假环境用自签证书模拟，未跑真实 ACME 流程 | 手册 S07，certbot 输出 `Successfully received certificate` |
| Cloudflare 代理（如果启用） | 取决于前辈的实际架构 | 手册"如果域名走 Cloudflare"小节：real-ip 配置 + SSL 必须 Full (Strict) |
| 公网访问、真实手机 4G 访问 | 假环境只在本机 | 上线后验证清单浏览器手工项 |
| 后台管理员登录后的操作 | 演练环境不知道真实管理员密码 | 由持密码的人登录验证（留言列表、编辑→预览→发布） |
| certbot 自动续期 | 需要真实证书 | 上线后 `sudo certbot renew --dry-run` |

## 五、结论

交付包与部署手册在干净 Linux 环境（Docker 模拟）下全流程走通，发现的 4 个交付物缺陷已修复并重新打包。**正式环境部署时的剩余风险集中在 DNS 与真实证书签发两个环节**，手册排查表已覆盖这两类问题的处理。

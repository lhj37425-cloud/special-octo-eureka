# 上线部署手册（前辈版）

> 这是给人看的部署 runbook。另有一份 `AI执行契约.md` 给 AI 助手用，两份步骤编号一致（S00–S12），可互相对照。
> 所有数字、路径、端口以 `部署事实.json` 为唯一事实源；本文与它有出入时，停下来找交付人确认。

## 30 秒速查

| 项 | 值 |
|---|---|
| 部署什么 | EVOL DREAM 三语官网（前台 Node + 后台 Node + Nginx 反代 + systemd 守护） |
| 服务器 | Debian 12 / Ubuntu 22.04+，Node ≥ 18，磁盘 ≥ 10GB 空闲（数据 + 14 天备份余量） |
| 域名 | `www.evoldream.tech`、`evoldream.tech`（DNS 先解析到服务器） |
| 拓扑 | Nginx 443 对外 → 前台 `127.0.0.1:4173`、后台 `127.0.0.1:4181`（后台挂同域 `/admin/`） |
| 代码位置 | `/srv/evol`，数据 `/srv/evol/data`，备份 `/srv/backup` |
| 数据量 | 28 条内容（专家 13/课程 2/案例 6/资质 7）+ 交付数据包 67 个被引用上传文件（约 197MB）；原始数据目录另有 11 个未引用旧图，未打包 |
| 交付物 | 代码包 `evol-app-<tag>.tar.gz`、数据包 `evol-data-<tag>.tar.gz`、`SHA256SUMS`、本手册 |
| 回滚耗时 | 约 5 分钟（停服务 → 解数据备份 → 起服务） |

**先读一遍「七、回滚」再动手**，知道怎么退，做的时候心里才有底。

> 数据包里有 `state.json`（管理员密码哈希）、客户留言和上传文件，**只走加密/可信渠道**（加密压缩、受控网盘或直连 scp），不要发群、不要提交 git。主管理员密码走单独渠道，不放在包里。

## 动手前你需要确认的 8 件事

- [ ] 1. 服务器是全新机器，还是已有站点在跑（已有站点：先备份原 Nginx 配置 `/etc/nginx/`）
- [ ] 2. 两个域名 DNS 已解析到这台服务器（`dig +short www.evoldream.tech` 应返回本机 IP）
- [ ] 3. 域名是否走 Cloudflare 橙云代理（走：部署完要做 S09 两件事）
- [ ] 4. 证书是新签（certbot，按 S07）还是已有（已有：改 `nginx.conf` 里证书路径）
- [ ] 5. 交付的代码包、数据包、SHA256SUMS 三个文件都已拿到并校验通过（S00）
- [ ] 6. 主管理员账号的密码你已单独拿到（凭据不写进任何文档，向交付人索取）
- [ ] 7. 80、443 端口没有被别的程序占用（`sudo ss -tlnp | grep -E ':80|:443'` 应为空或只有 nginx）
- [ ] 8. 有一个低峰上线窗口，出问题允许回滚

### 如果服务器已有站点（重要分支，先做这一步）

如果 `evoldream.tech` 已经指向这台服务器、80/443 上已有旧站，**不要直接按 S06 覆盖**。先做：

```bash
# 1. 备份现有 Nginx 配置和证书信息
sudo cp -a /etc/nginx "/etc/nginx.backup-$(date +%F-%H%M)"
sudo nginx -T > ~/evol-deploy/nginx-before.txt 2>&1
sudo ss -tlnp | grep -E ':80|:443'

# 2. 备份旧站数据、证书、crontab（路径按旧站实际情况改）
sudo tar czf ~/evol-deploy/old-site-data-$(date +%F).tar.gz /var/www /srv 2>/dev/null || true
sudo crontab -l > ~/evol-deploy/crontab-before.txt 2>/dev/null || true
```

然后二选一：

- **推荐：先在同机另一个端口/临时测试域名验证**，确认新站正常后再切 DNS；旧站保持不动。
- **必须原地切换**：先停旧站服务，保留旧站目录和数据库，不要删除；S06 的临时配置会占用 80/443，切换窗口内旧站会短暂不可用。
- 证书如果已有且覆盖两个域名，可复用：把 `nginx.conf` 里的 `ssl_certificate` 路径改成现有证书路径，S07 可以跳过。
- 如果必须新签证书，优先用 S06/S07 的 webroot 流程；`certbot --nginx` 会修改现有 Nginx 配置，已有站点时不要直接用。
- 切换后先按 S10 验证新站；失败时恢复 `/etc/nginx.backup-*`、重启旧站服务，再排查。

## S00 校验交付包（10 分钟，不做这步后面全白搭）

```bash
mkdir -p ~/evol-deploy && cd ~/evol-deploy
# 把交付的三个文件放到这里后：
sha256sum -c SHA256SUMS
# 预期输出：两个 .tar.gz 都是 OK；任何 FAILED 都停下，找交付人重新拿包

mkdir app data
tar xzf evol-app-*.tar.gz -C app
tar xzf evol-data-*.tar.gz -C data
ls app | head        # 预期看到 server.js、后台服务器.js、部署/ 等
ls data              # 预期看到 admin-backend、mvp-leads.json（都在顶层，不能再套一层 data/）
```

**失败处理**：包校验 FAILED → 停止，联系交付人重新拿包。不要试图修复数据文件。

```bash

# 必须 sudo：admin-backend 是 700/www-data，普通用户读不到 state.json
sudo bash /srv/evol/部署/预检.sh
# 预期末尾：PASS 全部 / FAIL 0 项，「预检通过，可以进入 S04」。有 FAIL 先处理
```

## S04 systemd 守护

```bash
cd /srv/evol
sudo cp 部署/evol-front.service 部署/evol-admin.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now evol-front evol-admin
sudo systemctl status evol-front evol-admin --no-pager
# 预期：两个都是 active (running)
```

**失败处理**：服务起不来 → `sudo journalctl -u evol-front -n 50 --no-pager` 看报错。常见是 Node 路径不对（`which node` 的结果要和 service 文件里 `ExecStart` 的路径一致）。

## S05 本机自检（门禁：不过不许配 Nginx）

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4173/vi/    # 期望 200
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4181/       # 期望 200
curl -sS http://127.0.0.1:4173/healthz                                 # 期望 {"ok":true}
curl -sS http://127.0.0.1:4181/healthz                                 # 期望 {"ok":true}
curl -sS http://127.0.0.1:4181/api/status                              # 期望 {"initialized":true}
```

**失败处理**：
- `initialized:false` → 数据没放对位置（S03 的 `/srv/evol/data` 层级错了，多套了一层目录）。**这时绝不要把端口暴露到公网**——空数据状态下任何人都能 POST `/api/setup` 抢注主管理员。
- 端口不通 → 回到 S04 看 journalctl。

## S06 Nginx 临时配置（HTTP-only，为拿证书做准备）

> 顺序不能反：全新服务器上证书文件还不存在，直接放带 `ssl_certificate` 的正式配置，`nginx -t` 必失败，certbot 也无法接管。

```bash
# ACME 验证目录：certbot 的 HTTP-01 会用到
sudo mkdir -p /var/www/html/.well-known/acme-challenge

sudo tee /etc/nginx/conf.d/evol.conf >/dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name evoldream.tech www.evoldream.tech;

    # 必须放在 location / 前面，否则会被下面的 return 200 拦截
    location /.well-known/acme-challenge/ { root /var/www/html; }
    location / { return 200 'ok'; add_header Content-Type text/plain; }
}
EOF
sudo nginx -t && sudo systemctl reload nginx
# 预期输出：syntax is ok / test is successful
# 先在服务器本机验证源站（不要依赖 DNS/Cloudflare）：
curl -sS -H 'Host: www.evoldream.tech' http://127.0.0.1/    # 期望 ok
```

**失败处理**：`listen [::]:80` 报错说明内核禁用了 IPv6（少见），删掉两行 `listen [::]` 即可——正式配置里同样要删。

## S07 签证书（certbot，webroot）

> 这里用 `certonly --webroot`，不改写 Nginx 配置，已有旧站时更安全。若服务器上已有覆盖两个域名的证书，可跳过本步，直接改 S08 配置里的证书路径。

```bash
sudo apt install -y certbot
sudo certbot certonly --webroot -w /var/www/html \
  -d www.evoldream.tech -d evoldream.tech --agree-tos -m 你的邮箱@example.com
# 预期末尾输出：Successfully received certificate
# 证书位置：/etc/letsencrypt/live/www.evoldream.tech/fullchain.pem

# 第一次不放心可先用 staging 试一次（不会占用正式签发额度）：
# sudo certbot certonly --webroot -w /var/www/html -d ... --staging
```

**失败处理**：
- `Failed authorization` → 九成是 DNS 没解析到本机（回第 2 项确认）或 80 端口被安全组/防火墙挡了（`sudo ufw allow 80,443/tcp` 或去云控制台开放）。
- 如果域名走 Cloudflare 橙云，HTTP-01 可能被代理/跳转干扰：先把橙云改灰（仅 DNS），签完再开；或改用 Cloudflare DNS-01。SSL 模式必须是 **Full (Strict)**。
- 检查挑战文件是否可访问：`curl -sS -H 'Host: www.evoldream.tech' http://127.0.0.1/.well-known/acme-challenge/测试文件`。

## S08 正式 Nginx 配置

```bash
cd /srv/evol
sudo cp 部署/nginx.conf /etc/nginx/conf.d/evol.conf
sudo nginx -t && sudo systemctl reload nginx
# 预期输出：syntax is ok / test is successful
```

## S09 仅当域名走 Cloudflare 橙云（不走就跳过）

1. CF 面板 SSL/TLS 加密模式选 **Full (Strict)**，不能是 Flexible——否则 CF 到 Nginx 走 http，后台登录 Cookie 不会带 `Secure`。
2. 在 `/etc/nginx/conf.d/evol.conf` 的 443 server 块里（`ssl_certificate` 行之后）还原真实访客 IP，否则限流和留言风控把所有访客当成同一个 CF 节点 IP：

```nginx
real_ip_header CF-Connecting-IP;
set_real_ip_from 173.245.48.0/20;
set_real_ip_from 103.21.244.0/22;
# ……CF 全部网段见 https://www.cloudflare.com/ips ，v4 和 v6 都要列
```

改完 `sudo nginx -t && sudo systemctl reload nginx`。

## S11 每日备份

```bash
# 一次性：建备份目录并授权给 www-data（cron 以 www-data 运行，目录不存在会直接失败）
sudo mkdir -p /srv/backup && sudo chown www-data:www-data /srv/backup

# 每天 3:30 打包数据目录，保留 14 天
sudo tee /etc/cron.d/evol-backup >/dev/null <<'EOF'
30 3 * * * www-data tar czf /srv/backup/evol-$(date +\%F).tar.gz --exclude='data/admin-backend/backups' -C /srv/evol data && find /srv/backup -name 'evol-*.tar.gz' -mtime +14 -delete
EOF

# 立刻手动跑一次验证命令本身没错：
sudo -u www-data tar czf /srv/backup/evol-first.tar.gz --exclude='data/admin-backend/backups' -C /srv/evol data
ls -lh /srv/backup/    # 预期看到 evol-first.tar.gz
```

说明：`--exclude='data/admin-backend/backups'` 是必须带的——后台自带备份目录（单份约 65MB）不打进每日包，否则每天约 200–380MB、14 天可能 3–5GB 撑爆磁盘。后台自带备份只留最近 10 份，代码里已自动控制。
异地备份建议**加密后再传**（包里有客户留言和账号哈希）：打包后 `gpg -c`，或 rclone crypt 模式同步到对象存储。

## 七、回滚（动手前先读一遍）

什么情况触发：S10 验证大面积 FAIL、页面白屏/样式全丢、后台登录不了且 5 分钟内找不到原因。

```bash
# 1. 停服务
sudo systemctl stop evol-front evol-admin

# 2. 数据回滚到最近一份每日备份（如果数据被改坏）
sudo tar xzf /srv/backup/evol-<日期>.tar.gz -C /srv/evol
sudo chown -R www-data:www-data /srv/evol/data

# 3. 代码回滚（如果新代码有问题）：重新解上一版 app 包覆盖，同样不动 data/
#    所以上线前要保留上一版代码包（至少保留当前这一份）

# 4. 起服务 + 验证
sudo systemctl start evol-front evol-admin
bash /srv/evol/部署/上线后验证.sh https://www.evoldream.tech
```

预期 5 分钟内恢复。恢复后通知交付人定位原因，不要在服务器上边修边试。

## 八、排查表

| 现象 | 原因与处理 |
|---|---|
| `nginx -t` 报 `ssl_certificate ... No such file or directory` | 证书顺序错了：回 S06→S07，拿到证书后再放正式配置 |
| certbot `Failed authorization` | DNS 没指到本机，或 80 端口被防火墙/安全组挡住 |
| `listen [::]` 报错 | 内核禁用 IPv6，删掉配置里两行 `listen [::]` |
| 表单提交返回 403「请求来源校验未通过」 | Nginx 没传 `Host` 或 `X-Forwarded-Host`，对照 `部署/nginx.conf` 的 `proxy_set_header` |
| 登录后 Cookie 没有 `Secure` | Nginx 没传 `X-Forwarded-Proto $scheme`；走 Cloudflare 则是 SSL 模式设成了 Flexible，改 Full (Strict) |
| 预览返回 401「请先登录后台再预览」 | 后台挂到了独立子域，改回同域 `/admin/` 方案 |
| 上传大视频报 413 | `client_max_body_size` 小于 60m，或没设 `proxy_request_buffering off` |
| 后台样式丢失、按钮点不动 | `/demo.css`、`/demo.js` 等 6 个绝对路径没指到 4181，对照正式配置补 location |
| 留言第 6 个人被拒 | 反代没传 `X-Real-IP` / `X-Forwarded-For`，所有人被当成同一个 IP |
| CSS/JS/SVG 响应缺 HSTS 等安全头 | 该 location 里写了 `add_header` 导致 server 级安全头不再继承，按 `部署/nginx.conf` 在块内重写 5 个安全头 |
| 服务重启后内容回到旧版 | 有人手改了 `state.json` 被后台覆盖；内容改动只能走后台页面 |
| 服务器已有旧站，改完配置旧站打不开 | 先恢复 `/etc/nginx.backup-*`，按“如果服务器已有站点”分支回到旧站；不要把旧站数据删掉 |
| 4173/4181 起不来，日志报 EADDRINUSE | 有旧实例占着端口：先 `sudo ss -tlnp \| grep -E ':4173\|:4181'` 找到进程，确认后再停 |
| 预检报“state.json 存在但当前用户不可读” | 没用 sudo：改 `sudo bash 部署/预检.sh` |

## 禁止事项（来自部署事实.json，违反必出事故）

1. 不要把 4173/4181 改成 `0.0.0.0` 直接暴露
2. 不要手改 `state.json`
3. 不要把后台挂到 `admin.` 之类的独立子域
4. 不要删除 `/srv/backup` 里最近一份备份
5. 上线窗口内不改代码，只部署交付的 tag 包
